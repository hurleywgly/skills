Prompt Caching, From the Inside

How the cache decides what survives, why long prefixes win, and the gotchas that erase your savings.

Engineering · Inference Notes
May 2026
8 min read

Prompt caching is the rare optimization that's both cheap to adopt and easy to misuse. Mark a long, stable prefix as cacheable, and the next call that reuses that exact prefix gets it back at roughly a tenth of the cost and a fraction of the latency. The whole story is in what counts as 'exact' and what counts as 'long enough.' This explainer walks the request path end-to-end, shows the exact API surface, and names the gotchas that quietly destroy hit rates in production.

How the cache decides

Every request enters with an ordered list of content blocks. The cache walks that list from the start and asks, for each block: have I seen exactly this content recently? The first block that doesn't match is where the cache stops contributing. Anything after that block is treated as fresh input — full price, full latency.

That ordering is the entire mental model. Stable content (system prompts, tool definitions, long static context) belongs at the front. Variable content (user messages, dynamic state) belongs at the back. Putting a single dynamic field — a timestamp, a session id — into the system prompt collapses your hit rate to zero, because the cache can't match past the first byte that changed.

The minimum-viable invocation

Marking a block as cacheable is one field. The block needs a minimum length — currently 1024 tokens for most models — and the TTL is short by default (5 minutes), which is the right tradeoff for chat-style workloads where the same prefix is hit many times in a session.

# Mark the system prompt as cacheable
response = client.messages.create(
    model="claude-opus-4-7",
    system=[
        {
            "type": "text",
            "text": long_system_prompt,        # 50KB+ ideally
            "cache_control": {"type": "ephemeral"},
        }
    ],
    messages=[
        {"role": "user", "content": query},
    ],
)
# 5-min TTL on the cached prefix; second call to this prompt
# pays only for the user-message tokens.
Cache hits don't survive small edits. They survive identical prefixes. The discipline is putting variation at the back.
— Inference team postmortem, after the templating bug erased a quarter of cache savings

Tradeoffs at a glance

The cache helps most when the prefix is long, the prefix is reused often within the TTL, and the variable tail is small relative to the prefix. The same conditions, inverted, are where caching stops paying off.

Dimension Helps when… Hurts when…
Prefix lengthPrefix is 10K+ tokens (system prompt, tools, RAG context)Prefix is short and hand-built per request
Reuse patternSame prefix hit many times within 5-min TTLCold-start workloads (rare, isolated requests)
Tail varianceUser message is small; rest is fixed contextEach request rewrites large parts of the prompt
StabilitySystem prompt is content-addressed and version-pinnedSystem prompt has timestamps, request IDs, or per-user data inline
Gotchas
  • Whitespace counts. A trailing newline added to the system prompt by your templating engine breaks every cache hit until something cycles it back.
  • Tool definitions are part of the prefix. Reordering tools — even alphabetizing them later — invalidates the cached prefix.
  • TTL is sliding from last hit, not from first write. A prefix that gets hit every 4.5 minutes can stay warm indefinitely; one that goes 6 minutes idle has to be rewritten.
